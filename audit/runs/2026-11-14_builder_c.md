# Run report: builder_c / M0.3 clients

- **Task and agent name:** builder C, M0.3: transport, classifier, base, pair, context, finmind, twse, tpex.
- **Files created or changed:** `src/twdata/clients/{transport,classifier,base,pair,context,finmind,twse,tpex}.py`; `tests/lead/{test_classifier,test_base,test_pair,test_finmind,test_twse_tpex,fixtures_inline}.py`; this report. Merged `main` once (section 15 and A/B code) before finishing.
- **Result:** 65 offline tests pass; `ruff check` and `ruff format` clean. No network, no token read.
- **Decisions I had to make:**
  1. `Response.rows` is the list of raw rows (lists, or dicts for OpenAPI and FinMind); `Response.fields` and `Response.records` (dicts keyed by field name) are additions. `Response.parsed` is the decoded JSON.
  2. `request_key` is duplicated in `base.py` (same formula as `rawcache.request_key`) so base has no import dependency on rawcache.
  3. `put_quarantine` is called with the same 8 arguments as `put` (the real signature has no `reason`); the reason is logged at WARNING instead.
  4. `EndpointSpec` has no `rows_path`; rows are extracted from `tables_key`, `table_selector` and top-level `data`/`fields`. A missing path is `drift`. TPEx rows without a `fields` list are `drift`.
  5. Cache hit: the cached body is re-classified; if it is no longer `ok` (for example calendar changed) the client refetches instead of failing.
  6. Zero-row ok responses whose body has no rows path (the no-data reply) give `rows=[]`, `fields=None`.
  7. `fetch` accepts an `EndpointSpec` or a key, plus extra keywords `store=False` (no caching, used by `user_info`), `dataset=` (override), `calendar=`. `Client.per_date(key, d, **kw)` helper added for pair.
  8. FinMind: HTTP status or in-body `status` 400 and 401 are `AuthError`; 403, 402, 429 and other 4xx are `BlockedError`; body or HTTP 5xx and status 0 are transient; a 200 body without `status` or with a non-numeric/3xx status is `drift`. Missing `FINMIND_TOKEN` is `AuthError` before any request. `user_info` is not cached and refreshes the quota limiter; `dataset()` re-reads it every `user_info_refresh_requests` calls.
  9. Era check date: `on` for per-date calls, the start date for range calls (section 15 item 10).
  10. `build_context` takes extra keyword-only test hooks (`limiter_factory`, `cache_factory`, `writers`, `calendar`, `sleep`). The initial QuotaLimiter limit is 600 until `user_info` updates it. `load_calendar` is looked up with `getattr` on `tradingcal` (absent at M0.3) and the calendar is only loaded when `data/clean/trading_calendar` exists.
  11. `allow_empty` is accepted by the per-date methods (`mi_index`, `otc`, ...). The pair raises `DriftError` for both-empty when the calendar gives no verdict (outside coverage or absent).
  12. The pair ledger skips a line if one with the same date and endpoints already exists, so a rerun does not duplicate.
- **Problems hit and how each was resolved:** Initial burst-rule and `exploratory` code was replaced by section 15 (`allow_empty`, no burst rule). An ok-empty no-data reply broke row extraction (fixed in decision 6).
- **What in my instructions was missing, ambiguous or wrong:** The task text and sections 8 and 11 still describe the 3-in-a-row 4xx rule that section 15 drops. Section 8 says `rows_path` on `EndpointSpec` but the code has `tables_key`. `put_quarantine` signature and `Response.rows` type are not given. Section 6 rule "per_date zero rows for a calendar trading day is drift" conflicts with the pair needing zero-row responses, resolved by `allow_empty`. The stub run in section 12 on dates outside the calendar needs `allow_empty` and a non-OK-stat reply on an uncovered date is still `drift` (rule 6), so the stub may hit `DriftError` on holiday replies with `stat` not OK; the Lead should check the real holiday reply shape.
- **What I would do differently next time:** Read section 15 first and merge main before writing code.
