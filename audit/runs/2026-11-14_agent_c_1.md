# Run report: agent C / M2 monthly revenue

- **Task and agent name:** builder C, M2 seed data: `monthly_revenue` ingest and spike S5 function.
- **Files created or changed:** `src/twdata/ingest/monthly_revenue.py`, `tests/agent_c/test_monthly_revenue.py`, `docs/data_dictionary/c_monthly_revenue.md`, this report. No fixtures of my own (the Lead's fixture is used).
- **Result:** 16 offline tests pass, full suite 175 pass, `ruff check` and `ruff format` clean. No network, no token read. No live rows collected (not in scope; the Lead runs the ingest and `check_unit`). From the fixture: 5 rows for 2330, `event_date` 2024-12-01 to 2025-04-01.
- **Decisions I had to make:**
  1. Column name is `revenue_month` (as in `schema.py` and the C spec), not `revenue_month_num` (m0 section 7 and 15.7). The code registry wins.
  2. `stock_list` reads `default_collection_set` (latest corrected, class none); missing table raises `MissingCollectionSet(RuntimeError)`, which the CLI maps to exit 5. A missing calendar (`ctx.calendar is None`) raises the same error, since `avail_revenue` needs it.
  3. Resume uses the state file's `completed` list read once at start; state is marked only after the stock's rows are written, so a crash leaves at most one stock to redo (the writer skips identical rows).
  4. `fetched_at` is `datetime.now(UTC)` taken when `finmind.dataset` returns (the client returns rows only, not the response `fetched_at`). It can be a few ms later than the raw cache time, and a cache hit gives a new `fetched_at`; both are harmless because identical rows are skipped.
  5. Extra drift checks beyond the spec, all fail closed: non-integer `revenue`, `revenue_year`, `revenue_month`; `revenue_month` outside 1 to 12. A float with integral value is accepted as int. Whole stock is not written if any of its rows fails (mapping happens before the write).
  6. The source `date` is not cross-checked with year and month (a mismatch would halt the whole run; the spec does not ask for it).
  7. `check_unit` matches the `t187ap05_L` fields by substring (`公司代號`/`Code`, `資料年月`/`Month`/`Date`, `當月營收`/`Revenue`) and the month as ROC `YYYMM` (`11312`), because no sample of that feed is saved in the repo. It raises `DriftError` if the stock-month is not found exactly once. The Lead should verify the field names on the first live run; the unit test uses assumed names.
  8. The `monthly_revenue` ingest does not call `check_unit` itself.
- **Problems hit and how each was resolved:** none blocking. DuckDB warned about `execute(...).to_arrow_table()`; switched to `con.sql`.
- **What in my instructions was missing, ambiguous or wrong:** m0 sections 7 and 15.7 say `revenue_month_num`, `schema.py` and the C spec say `revenue_month`. The C spec says "a column set that differs from the fixture's is DriftError" but does not say whether an empty response (no columns visible) is checked; an empty list cannot be checked. It does not say what `fetched_at` to use given the client returns only rows. No saved sample or field names of `/opendata/t187ap05_L` exist. `docs/specs/m0_specs.md` mentions `row_caps.datasets` but not a value for monthly revenue; 200,000 default applies (one stock for 10 years is about 120 rows). The tests rely on `tests/lead/fixtures_inline.py` through a `sys.path` insert because `--import-mode=importlib` does not make sibling directories importable; a shared test helper location would be cleaner. The collection_set refresh is expected to pick up new stocks, but the `done` state is per stock for the whole range: a later run with a wider date range will skip finished stocks (extending the range needs a state reset, which is a Human gate).
- **What I would do differently next time:** ask the Lead for a saved `t187ap05_L` sample before writing `check_unit`.
